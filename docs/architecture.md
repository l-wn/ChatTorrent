# Architecture

ClusterChat splits a language model across browser tabs. Each tab (a *peer*)
holds a contiguous range of the model on its own GPU through WebGPU; a token is
generated by passing the residual stream from peer to peer over WebRTC
datachannels until one of them samples it. A small Node signaling server
assigns ranges and relays WebRTC offers; everything else happens in the
browsers.

In the code and these docs, a cluster is called a mesh.

The model math is in [`model.md`](model.md).

## Positions

An `L`-block model has `L + 2` **positions**, the unit everything is placed and
routed on (`web/split.js`):

```
  0            1 .. L              L+1
  embedding    blocks 0 .. L-1     final norm + LM head + sampling
  (client.bin) (block_NN.bin)      (client.bin, lm_head.bin when untied)
```

The two ends are positions like any other, so their cost is budgeted and a
peer can hold either one without holding any blocks.

A peer holds a half-open range `[lo, hi)` of positions. Ranges may overlap and
may be any width. Two numbers describe the network, computed identically by the
server and every browser from the roster:

- `depth(x)`: how many ready peers hold position `x`.
- `r = min depth(x)`: 0 means the model cannot run, 1 means it runs but one
  departure breaks it, 2 means any single peer can leave.


## Joining

The handshake (`signal-server.js`, `net.js`):

```
peer   -> join     { v, room, chats? }      first, always: a join token, or null (global)
server -> welcome  { id, blocks, positions, minBlocks, weightsUrl, private, maxChats, ice, peers }
peer   -> capacity { cap, lo?, hi? }
server -> assign   { lo, hi }               null/null for a peer holding nothing
peer   -> have     { have }                 downloaded and warmed up to here
peer   -> ready    {}
peer   -> shrink   {}                       give back the unfilled tail
peer   -> grow     { lo, hi }               widened by one servable position
peer   -> release  {}                       give back everything (GPU lost); may claim again
peer   -> signal   { to, kind, sdp, mac? }  relayed to `to`, in the same mesh only
server -> roster   { peers }                broadcast on every change
server -> ping  /  peer -> pong             every 30 s; two misses drop the peer
peer   -> chat-start {}                     before a reply generates
server -> chat     { ok, max }              refused once `max` replies are generating
peer   -> chat-end {}                       the reply ended
```

**Replies at once.** Each mesh caps the replies generating at once. A page asks
for a seat (`chat-start`) before it shows a prompt and gives it back
(`chat-end`) when the reply ends. A refused prompt stays in the input with
"try again in a moment"; nothing reaches a GPU. A peer holds at most one seat,
and a seat is also freed when its socket closes or after `CHAT_LEASE_MS` (10
min). The global mesh's cap is `MAX_CHATS`. A private mesh's is chosen by its
creator (the page's "Private mesh limit", sent as `chats` in the join that
creates the room, ignored in any other join) and capped by
`MAX_PRIVATE_CHATS`, which is also the cap when the creator chose none. With no
answer to `chat-start` within 5 s the page goes ahead, so a signaling hiccup
never blocks a chat. This is the mesh-level gate; each runner still admits
sessions by its own frames (see KV cache and admission).

**Chats in memory.** Each mesh also fixes how many chats every peer keeps in
memory, its frame count (see KV cache and admission). The global mesh's is
`MESH_SESSIONS` (default 8). A private mesh's is chosen by its creator (the
page's "Chats in memory", sent as `sessions` in the join that creates the
room), capped by `MAX_PRIVATE_SESSIONS` (default 32), and `MESH_SESSIONS` when
the creator chose none. The welcome brings it as `sessions`, and a peer sizes
its Runner with it once, in `serve()`. A different number in a later welcome
(after a server restart) is logged and not applied until the tab reloads.
Peers need not agree on it: each sizes only its own memory.

Nothing is sent to a socket until its `join`; one that sends anything else, or
nothing for 10 s, is closed with code 4001, and a full mesh with 4002. A join
whose `v` is not `PROTOCOL` (`split.js`) is closed with 4001 too, so a mesh
never mixes pages that speak different versions of the messages below. The
page reports both instead of retrying.

Anything else that stops a socket short of its welcome (an error, a close, or
no welcome within 10 s, which catches a socket hung in CONNECTING) is retried
with backoff (1 s doubling to 15 s), the first join included; the page says it
is retrying and joins when a socket gets through. A socket is dropped once,
and only while it is the current one, so a late close from a socket already
given up on cannot open a second, orphaned replacement.

The server reads `checkpoint.json` (or `WEIGHTS_URL`), loads that checkpoint's
manifest for the model depth and dimensions, and sends the weights URL to every
peer, so the whole mesh runs one checkpoint.

A tab goes through three stages, each on its own schedule (`Engine`):

| stage | takes | needs |
|---|---|---|
| **join** (`connect()`) | ~1 s | the signaling socket |
| **ask** | ~1 s more | the manifest and the tokenizer; the composer opens here |
| **serve** (`serve()`) | minutes | WebGPU, the kernel and smoke self-checks, a range, the download, a warm-up pass |

Until it serves, a tab is a **client** (spectator): in the roster, linked in,
able to prompt and to relay, holding nothing. A tab whose GPU fails its
self-checks stays a client. What a tab holds is never part of whether it can
prompt.

**The ready gate.** The roster routes only through peers marked `ready`, and a
route works only over an open link. A WebRTC link opens about a second after
the claim that asks for it. So a peer's `ready`, and each step of its `have`,
is held back (`Mesh.#flush()` in `net.js`) until it has an open link to at
least one ready holder on each side it needs:
- position 0 (the hub), unless it holds it;
- the position just below its range;
- the position its holding hands off at.

A side with no ready holders imposes nothing. The holding goes out step by
step, as far as the open links reach. After `LINK_WAIT_MS` (5 s) it goes out
anyway, with a warning, so a peer that can never reach a neighbour still
serves. The status line shows "linking to peer N…" while it waits.

## Private meshes

Every tab joins the global mesh unless its URL carries an invite,
`peer.html#mesh=<secret>` (`web/room.js`). "Create private mesh" in the header
mints a secret (16 random bytes, base64url) and moves the tab into it; "Copy
invite link" hands it on. A private mesh is an ordinary mesh with a key:
every peer in it runs the same code and does the same work, and the server
keeps one `Room` (`signal-room.js`) per mesh, with its own roster, placement
and relay.

**The trust model.** The signaling server is untrusted. It sees metadata (that
a room exists, who is in it, their ranges and addresses) and can refuse
service. It cannot read a prompt, open a link, or sit between two peers:

- The secret is in the fragment, which a browser never sends, so no request,
  log, tunnel or link preview carries it. `peer.html` also sets
  `referrer: no-referrer`.
- The page derives two keys from it with HKDF-SHA-256 (salt
  `chattorrent/mesh/v1`):
  - the **join token** (`info "join"`), sent in `join`. Everyone with the invite
    derives the same one; the server files the room under SHA-256 of it and
    logs only the first six hex characters (the *tag* the page also shows, so
    members can compare);
  - the **link key** (`info "link"`), which never leaves the browser. Every
    offer and answer carries `mac = HMAC(linkKey, [1, kind, from, to,
    sdp.type, sdp.sdp])`, and a peer drops one that does not verify before an
    `RTCPeerConnection` sees it. The MAC covers the DTLS fingerprint in the
    SDP, so a datachannel only opens between two holders of the invite, and it
    covers both ids, so the server cannot relabel or redirect one.
- Since routing only ever sends over an open channel, every hop a prompt, a
  residual stream or a token takes is to a peer holding the invite. TURN
  relays see DTLS ciphertext.

**Failing closed.** A `#` that is not exactly `mesh=<22 base64url>` stops the
page before any socket opens: it never falls back to the global mesh. The
welcome says whether the mesh is private, and a Mesh that asked for one kind
and was given the other stops for good. `join` is resent on every reconnect. A
change of fragment reloads the page, so an engine never outlives the mesh its
URL names. The relayed `kind` must be `offer` or `answer`, so no peer can
hand another a forged `welcome` or `roster`.

**Limits.** `MAX_ROOMS` (1000) private meshes and `MAX_PEERS_PER_ROOM` (64),
both server environment variables. Peer ids are one counter across every mesh,
so they are never reused when a room empties and fills again.

## Claims, holdings and growth

A roster entry carries a **claim** `[lo, hi)` and a **holding** `[lo, have)`:
what was reserved, and what is downloaded, warmed and servable now. `have` only
rises. The browsers read the roster through `served()`, which projects each
entry onto its holding; the server places on raw claims, so two peers
downloading at once are not both sent to the same hole.

**Placement** (`place()` in `split.js`) picks the window whose sorted depth
profile is lexicographically lowest: fill uncovered positions first, then raise
`r`. Ties go to the lowest `lo`, except a one-wide claim, which lands in the
middle of the widest tied run.

**Capacity.** By default a tab claims the network's floor (`floorBlocks()`: the
smallest range worth holding, `MIN_BYTES` of weights) and grows from there.
URL parameters on `peer.html` pin it instead, which turns growth off:

```
?blocks=N    hold exactly N positions (0 = client)
?gb=N        hold as many positions as N GiB buys
?at=lo-hi    take exactly this range (a development knob)
?slow=ms     pause between downloaded positions
```

**Fill** (`Engine.#fill`). The Runner reserves KV for the whole claim, then
downloads positions in ascending order. Each is appended, checked (one pass
through the whole holding so far, as a real job runs it, that also checks the
output is finite), and announced with `have`. `ready`
goes out after the first one, so a peer serves the start of its range while the
rest downloads. If a download or allocation fails part way, the peer keeps what
it has and gives back the tail (`shrink`); if it holds nothing, it becomes a
client (`capacity 0`).

**Growth** (`Engine.#growClaim`). Once the claim is full, the peer keeps adding
one position at a time, toward whichever neighbouring position is less covered
(alternating on a tie), whenever its runner has been idle for 2 s. Each new
position is reserved, downloaded, checked with a pass through the whole holding
and only then announced with `grow`. Growth stops at a GPU allocation failure or
when the peer holds the whole model.
At the VRAM limit set in the page it *pauses* instead: the loop parks, and
`setVramLimit` wakes it, so raising or clearing the limit carries growth on from
the holding already in VRAM.

**A lost GPU** (`Engine.#onLost`). Some GPUs never fail an allocation: D3D12
on a shared-memory GPU pages idle buffers out, and only fails when one pass
needs more resident than fits, which loses the device. That is why every new
position is checked with a whole-holding pass before it is announced. On a
loss the peer sends `release` at once, so routing stops reaching it, then opens
a new device and reloads a smaller holding: the last one a check passed if the
newest position had not passed yet, else one position fewer than held. Growth
then stops at that size. After three losses, or below the minimum claim, the
peer stops lending until the page is reloaded.

**What a position costs.** The VRAM limit is held to bytes, so the two sides of
the comparison have to be real. What a peer *holds* is `Runner.vramBytes`: the
bytes `loader.js` measured as it uploaded each file, plus the KV page pool, the
session frames, the warm-up cache and the scratch, each counted as it is
allocated. What the *next* position will add is `split.js`'s `blockBytes(d,
{ index })` or `endBytes()`, read from the manifest's own file sizes
(`storedBytes()`), so the prediction is the number the measurement then
arrives at. On Qwen3.8-27B at q8:

| position | weights | state | total |
|---|---|---|---|
| a `linear_attention` block | 388.5 MiB | 8 recurrent states, 24.9 MiB; 2 replay slots, 6.9 MiB | 420 MiB |
| a `full_attention` block | 377.2 MiB | KV pool, 2 x 16384 tokens of int8 K and V, 72 MiB | 449 MiB |
| the embedding | `wte`, 1.26 GiB | none | 1.26 GiB |
| the head | `lm_head`, 1.26 GiB | none | 1.26 GiB |
| any peer | none | scratch, ~140 MiB at any context | once |

Each end uploads only the table it reads (`loadEmbed`, `loadHead`); a peer
holding both has two tables, and on a tied checkpoint one. The formulas in
`split.js` stand in only for a manifest with no file listing.

A new position only serves new sessions: a session's exit point on a peer is
pinned on first sight (see *Cuts* below).

## Links

Every peer computes the same link set from the same roster (`Mesh.wants`):

- **Forward.** A peer claiming `[lo, hi)` links to every holder of any position
  in `(lo, hi]`: every position where it might hand a job over.
- **Hub.** Every peer links to every holder of position 0, where its prompts
  enter and through which an answer addressed to it can be relayed.

The set is the symmetric closure of those and is not filtered on readiness (so
clients are linked in). A claim's `lo` only falls and its `hi` only rises
(except when a peer gives back a tail it never downloaded, which no session was
routed through), so a link a live session depends on is never pruned. The lower id offers.

A link whose ICE fails, whose channel closes, or that has not opened 30 s after
it was made is let go and offered again after a per-peer backoff (2 s doubling
to 30 s, reset once a link to that peer opens). The retry needs no roster
change. This matters for a spectator, whose only links are to the holders of
position 0: with one such holder, a failed ICE attempt would otherwise leave
it unable to prompt until someone joined or left. The higher id only drops its
end and waits for the new offer. ICE is gathered fully
before the offer is sent (no trickle), with STUN plus the TURN credentials the
server hands out in the welcome: one per peer for a TURN server of our own
(coturn's `use-auth-secret` scheme, `TURN_SECRET`), or a shared set minted
through Cloudflare's API.

**Relay only.** By default `peer.html` links only through the TURN relay
(`iceTransportPolicy: 'relay'`), and strips every non-relay candidate from an
outgoing SDP as a backstop. The only address a peer ever sees, in an SDP or on
a packet, is the relay's, so no peer learns another's IP; the signaling server
still does, from the WebSocket. The cost is one relay hop per link. It needs
TURN on the server: without it no link opens and the page says so.
`?direct=1` opts a tab back into direct links (a LAN with no TURN), at the cost
of showing its address to the peers it links to. The test harness links
directly unless given `relay=1`.

## Routing

A job carries a **cursor**, `pos`: the position its residual stream has
reached. The router (`route.js`) applies one rule to every message:

- a job whose cursor this peer holds is run from `pos` to a cut, then sent on
  with the cursor there. At the end of the line it is sampled and a `tok` is
  sent home;
- anything addressed to a linked peer goes straight to it;
- a job this peer cannot advance is forwarded to a ready holder of its cursor;
- an answer it cannot deliver goes to the hub.

Two invariants hold it up:

- **The cursor only moves forward.** A peer that cannot advance it must not
  pretend to.
- **A pin is never re-picked.** The peer a session's first job went through at
  a boundary holds that session's KV for the stretch after it. Choosing another
  holder later would answer from a cold cache, which produces wrong tokens and
  no error.

**Where a job stops** (`plan()`): decided on a session's first job at a peer,
then pinned (see Cuts). On an idle mesh it is the furthest position this peer
holds that someone else can pick up, preferring positions with an open link.
Hops dominate decode latency, so running further is better, and stopping short
lets the mesh route around a hole.

Under load it balances. Among the exits whose next peer reaches as far as the
furthest exit's would, so balancing never adds a hop, it picks the one where
the busier of the two peers ends up carrying least. A peer's busy time per
token round is `n * o + w * p`: `n` active sessions (`Runner.active`: those
that ran within `ACTIVE_MS`, 5 s, or have a job queued), `w` the positions they
run there (`Runner.load`), `p` its ms per position (`Runner.msPerPos`), and `o`
its fixed ms per job (`Runner.overheadMs`: reading back, sampling at the head,
logging the hand-off). The fixed part is why a path through fewer, larger
holders is cheaper. `p` is seeded from the warm-up pass each loaded position
gets (the first, which compiles shaders, is skipped); real decode tokens
replace it and measure `o`. Until every peer compared has a `p`, the idle path
is taken: counted in positions, a slow peer would look as fast as a quick one.
An earlier exit, which hands the next peer more, is skipped when that peer's
measured queue wait (`Runner.queueMs`) is more than 20 ms longer than mine:
the queue is measured, the model is an estimate.

Every ack carries the receiver's `w`, `n`, `p`, `o` and `q` (its queue wait),
so a peer learns the load of exactly the peers it hands work to, once per
token. A report older than 10 s, or none, counts as idle. Sessions planned
but not yet run, and sessions just sent to a peer, count for 2 s, since the
ack is sent before the job runs and does not include them yet. When several
peers hold the next position, `hops()` ranks them by the same cost plus each
link's measured ack round trip.

**Cuts** (`Runner.#exit`): `plan()` is a proposal. The first job of a session
entering a peer at a given cursor pins where that session leaves; later jobs
of the session leave there too, whatever the peer holds by then.

**Choosing a next hop** (`hops()`): a pinned boundary has exactly its pin. An
unpinned one ranks ready holders by open link first, then by reported load,
then by how far they reach. With no load reported, that is reach alone.

## Wire format

Messages are a JSON header plus an optional f16 payload (`net.js`):

```
[0..4)          u32 header length
[4..4+n)        UTF-8 JSON header
[.. pad to 4)
[..]            f16 payload (the residual stream, [n, hidden])
```

The payload is IEEE half precision (`web/f16.js`: round to nearest even,
values past ±65504 clamped to it). A Runner rounds the rows it hands on once,
where they leave it, and keeps those bits in its boundary log, so the next
peer, a replay and a repair all see the same values. On Qwen3.8-27B a row is
10 KiB, against 20 KiB in f32, at about 5e-4 relative error per hop (int8
was measured at about 1%, from outlier channels near 200 against an rms near
2). A reply therefore depends on where the cuts fall: it is identical for
the same path, and close to, not bit-identical with, a one-peer run.

Headers (`route.js`):

```
job   { k, s, key, from, pos, past, n, ids?, opts?, replay?, fill?, trace?, prof?,
        loop?, entry?, auto?, drafts?, rowOpts?, rb? }  + f16 [n, hidden] payload
ack   { k, s, to, at, past }
tok   { k, s, key, to, past, token, tokens?, eos, trace, ttl, fed?, head?, link? }
filled { k, s, key, to, past, n, trace, ttl }      a prefill chunk reached the end
err   { k, s, key, to, from, past, msg, busy?, nospec?, ttl }
fix   { k, s, key, to, from, at, rows, ttl }       a hand-off was repaired
free  { k, s, to, ttl }                             the session is over; drop its KV
halt  { k, s, key, to, ttl }                        stop feeding this session's loop
```

- `opts`: the sampler settings plus the repetition summary. The head clamps
  them to `LIMITS` in `model/sampling.js`.
- `loop: { id, left, ngram?, spec?, ctx? }`: the head feeds the token it
  samples back in as the next job, `left` more times. `id` numbers each loop
  the enqueuer opens. `spec` asks the head to draft (see Speculative decoding).
- `drafts`, `rowOpts`, `rb`, `tokens`, `nospec`: see Speculative decoding.
- `entry`: the peer that ran position 0 for this session, stamped as the job
  leaves it. `auto`: the head fed this job.
- `tok.past` is the job's `past`, so the enqueuer can tell this answer from a
  late answer to an earlier job. `fed` says the head already sent the token
  back in, `head` is who to send a `halt` to, and `link` is the timing of the
  head's hand-off to the entry.
- `busy` marks a capacity refusal, which nothing repairs or rebuilds.
- `fill`: a prefill chunk other than the prompt's last (see Sessions and
  generation). The head runs no LM head for it and answers `filled`.
- `err.past` is the failed job's `past`. The enqueuer drops an `err` below
  where its current prompt starts: a prefill chunk of an earlier turn, still
  in flight when that turn failed.
- `ack.past` is the acked job's `past`. Several prefill chunks can cross a
  boundary in a row, and an ack for an earlier one must not end the wait for
  the latest.

**Who may answer.** Session ids are guessable, so an answer is checked twice.
`key` is a random secret the enqueuer mints with each session. Every job
carries it, every `tok`, `filled`, `err`, `fix` and `halt` must echo it, and an
answer with the wrong key is dropped. A `tok` or `filled` is also only relayed
or accepted from a
link to a peer that could have produced or carried it: a holder of the last
position, or a hub (`Mesh.mayAnswer`). The sender is identified by the link a
message arrived on, not by a header field. A `free` is acted on only from a
peer that handed the session a job.

**Rate limits.** Each link may deliver at most 64 MiB/s and 5000 messages/s
(`RATE` in `net.js`). Anything over is dropped before it is reassembled or
parsed, and the sender sees it as a lost message.

Only a job at position 0 carries token ids. `past` is the session's context
length before this job, carried by the enqueuer, so runners track no positions.
A datachannel message is capped at 256 KiB, so a larger message is split into
fragments with a 16-byte prefix (`0xFFFFFFFF`, message id, index, count) and
reassembled at the far end; the channel is ordered and reliable. A channel with
more than 8 MiB queued takes no more jobs (headers on their own still go, up
to 12 MiB): the hop refuses the job as `busy`, see *KV cache and admission*.

## Sessions and generation

The tab that prompts is the **enqueuer**. It owns the session id, the token
history, and the prompt wrapping:

1. `turn.js` wraps the user's text in the checkpoint's chat format
   (`prompt.js`: `chatml`, `qwen`, `llama3`, or a plain `User:/Assistant:`
   transcript for base models). Qwen's thinking mode is off by default and
   rendered folded when on.
2. The prompt is sent in chunks of `T_MAX` (64) tokens, then one job per
   decoded token (see the closed loop below). Every chunk runs as one GPU
   pass. The prompt's chunks are pipelined (see Prefill).
3. The reply ends on end-of-text, on the token budget, on a full context
   (the cluster's context window, `ctx`), on Stop, or when `turn.js` sees the stop sequence, in which
   case the tokens past the cut are rewound out of the context. A
   full-attention layer's KV is addressed by position, so rewinding it is only
   a shorter `past` on the next job. A linear-attention (Gated DeltaNet)
   layer's recurrent state has already folded the cut tokens in and cannot
   give them back. On a hybrid checkpoint a rewind therefore marks the chat
   stale, and the next turn rebuilds it (see Chats).

**The closed decode loop.** Once a reply is under way, the token the head
samples is the next job's only input, so the enqueuer does not need to be in
the path. The prompt's last chunk carries `loop: { left }`. The head then routes
`[token]` straight to the session's `entry`, the peer that ran its position 0
and stamped its id on the job, while the `tok` goes home in parallel with
`fed: true`. With the enqueuer in the UK and every peer in Thailand, a token
therefore costs the peers' own hops instead of a UK↔Thailand round trip.

- **The enqueuer consumes answers as a stream** (`route.js`'s `decode()`). Each
  answer confirms the ids the job before it fed, so `history` is exactly what
  the peers hold at every point.
- **Where the loop stops:** the head stops by itself on end-of-text (which is
  not fed), when `left` runs out, and when the enqueuer leaves the roster.
  Stop sends a `halt` carrying the session key. The tokens already fed on the
  way arrive after it and are part of the reply, so Stop never forces a
  rewind.
- **Duplicates never feed twice.** A repair can re-send a hand-off that had in
  fact gone through, sometimes after the reply ended. Three rules stop such a
  copy from reviving a loop:
  - **Loops are numbered.** Every loop the enqueuer opens (a prompt, a
    re-sent token, a rebuild) gets a new id. The head never feeds a position
    of a loop twice, nor anything for an older loop.
  - **The entry accepts only the current loop.** It remembers the loop the
    enqueuer opened last, and any job from the enqueuer at position 0 ends the
    loop before it. A head-fed job of another loop is dropped there.
  - **Head-fed jobs continue exactly.** They are marked `auto`, and every block
    they cross must continue exactly where it left off (`Runner.#checkFed`),
    since only the enqueuer rewinds. One that is behind is dropped as stale.
- **Failures take the ordinary path.** A break is repaired locally, or it
  reaches the enqueuer as an `err`. The enqueuer then halts the old loop, frees
  the old session along its pins (so a loop a late repair revives dies at the
  entry), rebuilds, and reopens the loop with the rest of the budget.
- **The enqueuer takes over when the head can't close the loop.** A head with
  the loop off answers without `fed`. So does a head whose link to the entry is still
  opening, or one that has no context for the penalties after a repair moved
  it. In each case the enqueuer feeds that token itself and asks again. The
  Decoding setting (closed loop / round trip) switches the loop off.

**Prefill** (`route.js` `sendFills()`). Every chunk of a prompt but the last is
a prefill chunk (`fill: true`). Up to `PREFILL_WINDOW` (4) of them are in
flight at once, so the peers on a path work on different chunks at the same
time instead of waiting for each chunk's round trip. The last chunk follows as
soon as the last prefill chunk is sent; it is the ordinary job that samples
the first token and opens the loop.

- **The last chunk commits the prompt.** Links are ordered and a runner runs a
  session's jobs in order, so its answer means every chunk before it ran. A
  lost chunk makes the next one fail `Runner.#checkFed`, which comes back as an
  `err`. So `history` gains the whole prompt with that answer, and a failure
  rebuilds with all of it. A rebuild sends its context the same way.
- **No LM head for a prefill chunk.** The head runs no final norm, LM head or
  sampling for it and reads nothing back. It still fills the MTP head's KV and
  keeps its last row for the next job, then answers `filled`. The `filled`
  answers only pace the window and report progress.
- **The head samples one row.** A job other than a verify runs the final norm
  and the LM head on its last row only, not on all of its rows.
- **Repairs.** A local repair replays the boundary log up to the job it
  re-sends, which covers any earlier chunks still in flight, and its `fix`
  tells the enqueuer to stop waiting for them.
- **A refused prompt.** A prompt refused for capacity partway through leaves
  the chunks already sent (at most the window) to run on the peers before the
  one that refused.
- **Other chats.** Each prefill chunk can sit in a runner's queue ahead of
  other chats' decode jobs, which is why the window is small. Runners take
  queued jobs first come first served; `Runner.#next()` is where a policy that
  runs other chats' decode jobs ahead of prefill chunks would go.
- **Next for prefill speed:** the prefill GEMM. `matmulTiledSrc` and
  `matmulTiledQ8Src` (`kernels.js`) are plain 16x16 shared-memory tiles, so a
  64-row chunk reads each weight four times from memory, with no register
  tiling or double buffering. pooled's register-tiled, double-buffered GEMM
  made its prefill pass 1.64x faster.

**Sampling** happens on the peer holding the head, which has the logits but no
token ids. Each job's `opts` carry a short repetition summary (`jobOpts()`,
built from `penaltyState()`): the most repeated recent ids with counts, and the
ids that would complete an n-gram already in the context. The enqueuer builds
it for the jobs it sends. Under the closed loop the head builds it for the jobs
it feeds, from the whole context, which the loop's first job carries once and
the head then keeps up to date.

The head selects each sampled row's raw top M logits on the GPU
(`kernels.js` `topkRows`, in the same submit as the LM head) and reads back
only those (value, index) pairs. M is the top-k plus the number of penalized
and banned ids (`sampling.js` `candidatesFor()`; 1 for greedy with no
penalties). Every penalty only lowers a logit, so those M hold every token the
whole row could give, and `sampleFromCandidates()` runs the sampler's own
arithmetic on them and returns the same token for the same random draw. A row
that needs the whole vocabulary (temp > 0 with no top-k, or M above 256) is
read back and sampled whole.

## Speculative decoding

With the page's Speculative decoding setting on (closed loop only), the head
drafts the tokens after the one it sampled and the mesh checks them in one
pass. A hop costs about the same for a few rows as for one, so each accepted
draft is a token that took no lap of its own. The reply is the reply plain
decoding gives.

**Drafting** (`route.js` `feed()`, `web/draft.js`). The head keeps the
context (the loop's first job carries it, as for penalties). It looks for the
most recent earlier place the context's last 4 to 2 tokens occurred and
proposes what followed, up to K tokens. K is picked per session from
{0, 3, 5, 7} by measured tokens per second; 0 is a plain step, so a busy mesh
falls back to plain decoding. Fewer than 2 drafts are not sent. With
penalties on, the drafts stop at the first one its own row would ban (the
no-repeat n-gram block bans exactly the copies lookup proposes).

**The verify job** carries `ids = [token, ...drafts]` and `drafts`, so
`n = drafts + 1` (at most `SPEC_COLS`, 8). Every peer runs the rows as usual.
The head reads back every row's logits and samples row i with the repetition
summary plain decoding would have used for it (`opts` for row 0, `rowOpts[i-1]`
after, built assuming the drafts before it were accepted). Drafts are accepted
while they equal their row's sample; the first mismatch, or the sample after
the last draft, is the next token. The `tok` carries `tokens`: the accepted
drafts and that token, cut after end-of-text. Accepted drafts spend the loop's
budget and reach the enqueuer as fed answers.

**Rollback** (`Runner.#checkFed`, `model.js` `linearBlock`). The next job
starts at `past + tokens.length`, so each block tells from `past` alone how
many of the verify's rows the session keeps. A full-attention block's KV is
addressed by position and needs nothing. A linear_attention block's recurrent
state folded every row in, so a verify job records, in the session's replay
slot, the state and conv rings from before it and its own per-token
projections. When the next job keeps k < n rows, the block puts the state back
and re-runs the same kernels over the first k rows before the job's own work,
in the same submit. The restored state has the bits k plain steps leave.

- Each block accepts the next job anywhere in `(base, base + n]` after a verify
  of n rows from `base`; outside it the usual rules apply. A duplicate of the
  verify (`past == base`) is stale.
- Everything is per session: the window lives on the session's frame and the
  replay data in its own slot, so chats interleaving on a Runner never touch
  each other's. A runner keeps at most `specSlots` (its `slots` by default)
  replay slots, leased on a session's first verify and returned with its frame.
- A verify that finds no free slot, or no GPU memory for one, is refused with
  `err { nospec }` before anything changes. Nothing repairs it. The enqueuer
  re-sends the token the head fed as a plain job with `rb`, which lets the
  peers that ran the verify roll back to `base`, and decodes the rest of the
  turn plain.
- A turn that ends on a verify (end-of-text or the budget) leaves its rejected
  rows in place. The next turn's first job starts inside the window and rolls
  them back like any other.


**The context window** is a cluster setting, like `sessions`. The creator
picks one of `split.js`'s `CONTEXTS` (4K, 8K, 16K or 32K tokens; `DEFAULT_CTX`
is 16K) on the create page. The join carries it, the server keeps it on the
room (capped by `MAX_PRIVATE_CTX` and the model's `n_pos`; `MESH_CTX` for the
global mesh) and the welcome hands it to every tab, which sizes its Runner and
checks prompts against it. A Runner is sized once, so a tab keeps its window
until it reloads. KV is int8 (see docs/model.md, Paged KV cache), so 16K costs
about the VRAM that 4K did in f32. A Runner refuses to start if one layer's
pool buffer is larger than the GPU can bind.

Each Runner has a **page pool**: one buffer per full-attention layer for K and
for V, cut into 64-token pages, sized for `poolSlots(sessions)` full contexts:
one per `SESSIONS_PER_SLOT` (4) sessions, so 2 at the default 8. Each of the
mesh's `sessions` **frames** holds one session's page table and, on a hybrid
checkpoint, its recurrent state. A chat is charged for the pages it uses, so
the frames share the pool rather than each reserving a full context. On
Qwen3.8-27B at 16K each session beyond 8 costs about 335 MiB across the whole model.

A session's frame or pages may only be taken from a session that has been idle
for `IDLE_MS` (2 s), counted from the end of its last job here. A session with a
job queued or running at a peer is never idle there, however long the queue. If
every frame belongs to an active session, a new session
waits in line at that peer (`Runner.waiting`), first come first served, and
takes the first frame to go idle or be released; the jobs of the chats already
running are not held up behind it. One that has waited `WAIT_MS` (30 s) is
refused with a `busy` error, as is a job that needs KV pages nobody idle can
give up, and nothing repairs or rebuilds a `busy`. A hop whose link to the next peer is
backed up refuses the same way: the peer is there, and a replay or a rebuild
would only add to the queue that is full. So does a runner holding jobs for
`MAX_QUEUE` (32) sessions, for a new one, or `MAX_SESSION_QUEUE` (8) jobs of
one session. After a refusal, the same prompt's next chunk (already on its way)
finds the cache behind it; it is refused as `busy` too, not as an evicted
cache, so no repair runs a prompt the enqueuer has given up on. When a chat is deleted, the enqueuer
releases its own cache and sends `free` along the pinned chain; idle eviction
covers any `free` that never arrives. Starting a new chat or switching away
frees nothing: the old chat is parked, and its caches stay until idle eviction
takes them.

Each frame counts, per block, how many rows it holds for its session
(`Runner.#checkFed`). A job may start at or below that count on a
full-attention block, but never above it: those rows were never written. On a
linear-attention block it must start exactly at the count, since recurrent
state can only be continued or restarted. A job at `past` 0 restarts it,
clearing the state first. Anything else is refused with the same error as an
evicted cache, so it takes the same road home. That road covers a parked chat
whose caches are partly gone, a pin that was dropped and re-picked onto a
different frame, and a replay running into a peer that still holds the
session.

## Chats

A tab can hold many chats. To the router a chat is a **conversation**
(`makeConversation()`): its token `history`, and the session id and key the
peers hold it under. One conversation is active and the others are parked.
Sessions are minted on a chat's first job.

- **Switching** (`switchTo()`) swaps the active conversation and keeps the old
  one's pins. Switching back reaches the same caches if they are still there.
  If they aren't, the first job comes back `no longer cached` and the ordinary
  failure steps apply: a local repair if only part of the path lost it, and
  otherwise a rebuild, reported as a **resume**.
- A conversation that has a history but no session (a chat loaded from
  storage), or one marked stale (a rewind on a hybrid checkpoint, or the chat
  changed in another tab), is rebuilt before anything is sent. This doesn't
  count against the turn's repair budget.
- The router refuses to switch while a reply is in flight, and so does the
  Engine for the whole of `generate()`.

**Storage** (`web/history.js`) keeps each chat in IndexedDB: its messages as
shown, its token ids exactly as the peers were fed them (after any rewind),
and the model and checkpoint that tokenized them. The hidden state is never
kept. It is spread across the peers and far too big, and the ids rebuild it
exactly. A chat whose model or checkpoint differs from the mesh's opens
read-only. The browser is asked once for durable storage, and a
`BroadcastChannel` tells the site's other tabs about every change.

**A chat runs only in the mesh it was made in.** Records are filed under the
mesh's `historyTag`: `global`, or a value derived from the invite with HKDF
under its own label (room.js). It is never the secret, the join token or the
public tag. A store opened for one mesh can't list, read, write or delete
another mesh's chats. The router checks the tag again before a switch. A
private mesh's list shows how many chats other meshes hold, and never their
titles.

**The chat list** (`peer.html`) is a drawer on a narrow screen. At 1100 px and
up it is a sidebar that stays open, and the header button docks and undocks
it. Chats are grouped Today / Yesterday / Earlier, and each can be renamed and
deleted. The export format is defined (`exportChats()`/`importChats()`:
`{ format: 'chattorrent-chats', v: 1, chats }` with ids as base64 LE u32), but
there is no UI for it yet.

## Failures

A peer can leave at any time. Recovery works in steps, cheapest first:

1. **Acks.** The receiver of a job acks it before touching the GPU. No ack
   within 1.5 s counts as a failed send.
2. **Local repair.** Each peer keeps a **boundary log**: the residual stream it
   handed over at each boundary, per session (`Runner.logs`), as the f16 bits
   it sent. When a hand-off
   fails, the peer that made it picks another holder, replays the log into it
   (as `replay` jobs, which rewrite KV all the way down the line) and re-sends
   the job. The enqueuer only gets a `fix` notice. A log that was started again
   (its session was released or evicted there and re-admitted by a shorter
   replay) is never replayed past its end, since those rows would be zeros. It gives up after 2
   consecutive repairs at one boundary, or when the log is longer than 256
   tokens (a replay costs as much as a prefill).
3. **The error walks back.** A failed hand-off sends an `err` one hop back, to
   the peer that handed the job over, which tries its own local repair, and so
   on towards the enqueuer.
4. **Rebuild.** The enqueuer re-prefills its whole history under a new session
   id (`recover()`), so no stale pin, cut or cache can be reached. It reports
   progress and can be cancelled. At most two rebuilds are spent per turn,
   including one tried again after the first failed.

A job that gets no answer at all times out after 5 minutes.

Known gaps:

- Growth is not gated. Links to a grown peer's new neighbours are only wanted
  once its wider claim is announced, so they can't be waited for first.
  Routing picks linked peers first, which covers every case except growth into
  a position nobody else holds. There, the first job can fail until the link
  opens, but the mesh couldn't answer before the growth either.

- A peer that stays connected but stops answering (a zombie) at the enqueuer's
  first hop: every rebuild can be routed straight back into it until the roster
  drops it, so a turn can spend its whole repair budget there.
- Peers are trusted: nothing checks that a peer computed its range honestly.
- Routing balances GPU work, not chats: every chat still needs a frame on the
  embedding's holder and on the head's, so with one of each the runners'
  `SESSIONS` caps concurrent chats however the middle is split.
- Reachability is not in the roster, so depth counted over peers that cannot
  reach each other is optimistic.
- One job queue per runner, first come first served, so a long prompt's
  prefill chunks delay other chats' decode jobs on the same peers (by at most
  `PREFILL_WINDOW` chunks each).
- A session waiting for a frame at one peer is idle at the peers before it, and
  can lose its frame there if it waits past `IDLE_MS`; its next job then comes
  back `no longer cached` and the chat is rebuilt.
- Downloaded weights are not cached across page loads beyond the HTTP cache.
- Private meshes hide content, not metadata: the server sees who is in a room,
  and anyone holding a room's join token (the server does) can enter its
  roster and claim positions nobody can route to. That is a denial of service,
  not a leak. Peer ids are global, so a room's members can infer roughly how many
  tabs have joined the server. An invite is as secret as wherever it was
  pasted (browser history and sync included); anyone holding it is a member.

## Precision and limits

Weights are f32, f16 or q8 (see `model.md`); everything else is f32. Every page
asks for 2 GiB buffers (clamped to the adapter), enough for Qwen3.8-27B's
~1.27 GiB q8 `wte` and `lm_head`. An untied `lm_head` ships as its own
`lm_head.bin`, because some browsers cannot fetch a single body over ~2 GiB.

Files are fetched whole first, so the browser and Cloudflare can cache them;
after a failure, a file is fetched in 8 MiB ranges with retries.

## Profiling

The mesh page's profile setting asks every peer on a job's path to time it
(`prof` in the job header): level 1 times each hop's compute pass with GPU
timestamps, level 2 times every kernel. Each hop appends its phases (queue,
encode, submit, GPU wait, readback, sample) and link round trip to the job's
`trace` (`queue`, `encode`, `submit`, `wait`, `copy`, `sample`/`log`, plus
`plan` and `ui` from the router), and `web/profile.js` summarises them under the
reply.

## Testing

```
npm test            the Node suites in tools/*.test.mjs (no GPU)
npm run test:gpu    builds a tiny model (tools/tinymodel.mjs) and runs
                    tools/mesh.gpu.test.mjs: real peers in headless Chrome tabs
```

- `split.test.mjs`: placement, costs, coverage.
- `room.test.mjs`: invite parsing (failing closed), the key schedule against a
  pinned vector, the seal rejecting every tampered field, and a `historyTag`
  that shares nothing with the secret, token or tag.
- `history.test.mjs`: saved chats kept to their mesh, round trips, titles and
  day groups, cross-tab notices, export and import. `web/dev/history.html`
  runs the same checks against a real IndexedDB.
- `net.test.mjs`: the Mesh getters and the signaling server over real sockets,
  including rooms kept disjoint, the join, the caps, a log that never carries a
  token, and a Mesh that refuses unsealed offers and a mesh it did not ask for.
- `stage.test.mjs`: a chain of Runners over a stub GPU, against the single-tab
  dispatch order, for every way of cutting the line.
- `mesh.test.mjs`: N routers over N Runners on a simulated wire, with a digest
  model standing in for the numbers. It covers repairs, rebuilds, evictions and
  growth, plus a seeded soak that kills peers at random (`--seed N` to
  reproduce). It also covers:
  - chats: resuming warm, after eviction and from storage;
  - a rewind or a replay through recurrent blocks, whose toy state folds
    cumulatively the way DeltaNet's does;
  - the closed loop, held to the round trip's tokens and context across every
    cut, placement, stop, failure and old head;
  - speculative decoding, held to plain decoding's tokens and context across
    every cut, budgets, end-of-text inside a verify, `nospec` refusals,
    several chats at once, and each verify row's penalty summary.

  `--fuzz N` (`--fuzz-seed S`) draws random meshes, people, conversations,
  halts, cuts and departures. Each turn is replayed against a single peer's
  round trip, and afterwards no loop may still be feeding.
- `engine.test.mjs`, `sampling.test.mjs`, `prompt.test.mjs`,
  `profile.test.mjs`, `loader.test.mjs`, `tokenizer.test.mjs`: the individual
  pieces. `parse.test.mjs` checks every browser module parses under Node (a
  stray backtick in a WGSL comment ends the template literal). Tests that need a local tokenizer
  skip when it is absent.
- `mesh.gpu.test.mjs`: several people prompting at once across many peers on a
  real GPU, with greedy decoding diffed against a single peer.
  - The reference decodes with the round trip, and every other row with the
    closed loop unless marked otherwise.
  - Rows check that the loop really closed at the head, and that nothing still
    runs once the replies have ended.
  - `--fuzz N` runs random scenarios, each replayed against a one-peer
    reference held in a private room.
  - Options: `--only NAME`, `--wire bc` (BroadcastChannel instead of WebRTC),
    `--prompts N`, `--heavy`, `--show`.
  - It aborts on a software adapter. Each tab loads `web/dev/harness.html`.

`web/dev.html` runs the kernel tests, the speculative decoding tests
(`web/dev/spec.test.js`: a DeltaNet block that verifies n rows and keeps k
holds the state and gives the output of k plain steps, to the bit, at small
and at Qwen3.8-27B's head shapes, sessions interleaved), the smoke check, the
tokenizer self-test, and a full oracle diff and generation in one tab. Parameters:
`?weights=<url>`, `?oracle=<url>`, `?stream=1` (verify a block at a time, for
a model larger than this GPU), `?decodeSteps=N`, `?bench=…`. The oracle dumps in
`oracle/` come from `tools/dump_*_oracle.py`.
